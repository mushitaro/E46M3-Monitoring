## 0. 方針転換の根拠（なぜホストを外すのか）

**ホストを維持すると Cloudflare 配信が成立しない。** Chrome 142 以降、パブリックオリジン（HTTPS）から
ローカル/ループバック宛の要求は **Local Network Access 権限**なしで**ブロック**される。加えて現行ホストには
`Access-Control-Allow-Origin: *`（`host/Program.cs:64`。コメントは "localhost のみ許可" と書いてあるが実装は `*`）
と無認証の `POST /api/job`（`:102-110`）があり、ケーブル接続中は**任意のWebページがECUを叩ける**。
さらに利用者全員に `C:\EDIABAS`（BMW proprietary）の導入と .NET ホストの起動を要求する。
「URL を開くだけ」という製品像とは両立しない。

**外しても機能は失われない。** 3つの既存資産がそれを可能にする：

| 資産 | 場所 | 何を与えるか |
|---|---|---|
| CSL tuner の `dme-link` | `E46M3CSL_TuningTool/src/lib/dme-link/` | 実車で鍛えた DS2 スタック一式（後述） |
| **`prg_ds2_telegrams.py`** | `MSS54-DS2-Tool-Public-1.2.1/analysis-tools/` | **SGBD `.prg` から「ジョブ名 → DS2要求テレグラム」を車なしで静的抽出**。MSS54分は `ds2_telegrams_out.txt`（510行）として既に出力済み |
| `DmeLiveValueCatalog` / `ErrorDescriptionCatalog` | `MSS54-DS2-Tool-Public-1.2.1/` の解析結果 | MSS54 の**ライブ値 8ブロック・約213項目**（`DATALOG-items-JP.md`）と DTC 本文カタログのスキーマ |

`ds2.ts` が実装しているのは EDIABAS のジョブ体系ではなく**生の DS2 制御バイト**で、これは **ECU 非依存**：
`READ_ERROR_MEMORY 0x04` / `CLEAR_ERROR_MEMORY 0x05` / `READ_MEMORY 0x06` / `WRITE_MEMORY 0x07` /
`READ_IO_STATUS 0x0B` / `SET_IO_STATUS 0x0C` / `REQUEST_LOGIN_SEED・SEND_LOGIN_KEY 0x90` /
`KEEP_ALIVE 0x9E` / `END_DIAGNOSTIC_MODE 0x9F`。SMG II(0x32) / DSC(0x56) にもアドレス違いで同じ制御バイトが効く。

**副次的な収穫** — 旧計画で「実車でしか確定できない」としていた項目のいくつかが既に解決済み：
- MSS54 の **SEED_KEY 鍵アルゴリズムは `ds2.ts:202 calculateLoginKey()` に実装済み**（"BMW"＋アクセスレベル5 →
  46バイトのシード応答から4バイト鍵を計算。長さ5の応答は「既に解錠済み」）
- 否定応答テーブル（`Ds2Status`: `A0/A1/A2/B0/B1/FF`）— 現行アプリには存在しない
- エコー不一致の**電気的故障 vs desync 分類**（`classifyEchoMismatch()`）— 開放コレクタは 1→0 にしか倒せない、
  という物理から判別する。lag 0..3 のずれも試行して当てはまりを採点する
- **5-baud init も fast init も不要**。ポートを開いてフレームを交換するだけ

### ⚠ 現行アプリの Web Serial 経路は、生きていたとしても動かなかった

`js/serial.js:24` は `parity: "none"`（8N1）。tuner は **8E1 が必須**と実測で結論している：

> 8N1 の受信側はストップビットのあるべき位置でパリティビットをサンプリングするため、
> **ポップカウントが偶数のバイトすべてでフレーミングエラーが出る**。DS2 の
> アドレス `0x12` と ACK `0xA0` はどちらもポップカウント2なので、事実上すべてのフレームが
> 先頭バイトで落ちる。

つまり現行の直結経路は「到達不能な死にコード」であると同時に**設定自体が誤っていた**。
`dme-link` に置き換えることで解消する。

**ホストは死なない、降格する。** `host/` と `tools/` は**ビルド時のデータ生成ツール**として残す
（SGBD からのジョブ表・テレグラム・DTC本文の抽出）。実行時依存ではなくなる。

### 正直な留保

1. **テレグラム抽出は `.prg` バイトコードの静的スクレイプ**。出力を見ると複数ジョブが同一の
   `12 09 06 00 00 00 00 02 1f` を共有しており、**引数によるアドレス置換**が明らかに絡む。
   条件分岐・ループ・引数依存アドレスを持つジョブは静的抽出では完全に捕まらない。**要検証**であり、
   検証できないジョブは出荷対象から外す（＝§4 の検証台帳の入口）。
2. **SMG II / DSC のライブ値ブロック配置は存在しない**。MSS54 の213項目に相当する作業が2モジュール分必要。
   これが本計画で最大の新規実装。
3. **出所（provenance）**：`decompiled-source/`（第三者ツールの逆コンパイル）と BMW SGBD 由来データの双方に
   由来する。プライベートリポジトリ＋Cloudflare Access で緩和するが消えはしない（§7-3）。

### 移植時に必ず守る作法（実車で代償を払って得られたもの）

- **「バイトを待つ、時計を待たない」** — `readExact` は完全にイベント駆動。応答の完結は**DMEが返した長さバイト**が決め、
  タイマーやアイドルギャップでは決めない。ただし**長さを信用する前に `header[0]` のアドレスを検証する**
  （フレーム外れ時、でたらめな長さは次の応答まで飲み込むか、タイムアウト丸ごと待たせる）
- **余剰バイトは捨てない** — `splice` で保持。エコーと応答の先頭が同じ `reader.read()` チャンクで届くことが頻繁にあり、
  「1チャンク＝1 readExact」にすると必ず desync する
- **`exchange()` の中では resync しない** — リトライを持つ層の責任。ここで resync すると、フラッシュ中に latch を
  黙って消し、DME リセット後にフォールバックが破壊的コマンドを再送しうる
- **遅延を先に、resync を後に** — 逆にすると DME の遅れて来た応答が空になったバッファに入って次の試行を desync させる。
  また `purge()` だけでは latch した break を消せない
- **フレーム間ディレイは入れない** — 0/5/10/20/40ms を実車で掃引して**何も変わらなかった**（turnaround は全設定で
  104–121ms）。9600 で 538 チャンクなら 40ms は 21 秒の純損失。害しかないノブは残さない
- **ボーレート切替は実装しない** — 実在するのは 9600 / 38400 / 125000 の3つだけ（19200 は `0xB0 PARAMETER_ERROR`）。
  **38400 は切替もワイヤ速度も成功するのに ECU が無言になり、538チャンク中 0/1/4/7/9/17 で死ぬ**（≈14%/chunk）。
  125000 は両プロセッサのフラッシュを消去する fast entry が要る。**診断アプリは 9600 固定でよい**
- **コメントは仕様である** — `dme-link/` の体積の約1/3が、測定値・訂正・棄却した仮説・各ガードを生んだ事故の記録。
  剥がすと定数が恣意的に、ガードが除去可能に見える（実際に一度除去され、そのときの推論が誤りだったと記録されている）

**未決の1点：セッション終了をどうするか。** `0x9F END_DIAGNOSTIC_MODE` は `ds2.ts:35` に定数として存在するが
**tuner も呼び出していない**（ポートを閉じるのが実質の teardown）。チューナーは1ECUを相手に、走行後に必ず切断する
使い方なのでそれで足りている。診断アプリは**3モジュールを切り替えながら使う**ため、ECU切替と切断で `0x9F` を
送るべきかは実車で確かめる価値がある（送らないと前のECUがセッションを保持したままになる可能性）。
core に実装だけ用意し、送るかどうかはアプリ側の判断にする。

### 現行アプリが違反していて、移植で解消される点

- ホスト通信に**タイムアウトが無い**（`AbortController` はリポジトリ全体で0件）→ 固まると UI は busy のまま出口なし
- **リトライが皆無**（`retry|attempt` の該当0件）
- **排他が無い**：`_ediabas` はスレッドセーフでない単一インスタンスに Kestrel が並行アクセス → CommandGate で解決
- **keep-alive が無い** → 確認モーダル表示中にセッションが落ちる
- `beforeunload` / `pagehide` / `visibilitychange` が**1つも無い** → tuner の `useUnloadGuard.ts` で解決

### FTDI Latency Timer について（現行ドキュメントの是正）

`host/CONNECT-VEHICLE.md:33-40` は「1ms 必須。怠ると必ず失敗する」と書いているが、これは**検証されていない通説**。
FTDI 自身の AN_107 は 1ms を**非推奨**とし、D2XX ガイドは有効範囲を 2–255（既定16）としている。
CSL tuner の実測では wakeup が 135→14 に減った一方で転送は **5.7% 遅くなった**。
**掃引して測る**（1→4→8→16）。1ms を前提にした記述は書き直す。

### Web Serial の実装上の事実（設計に影響する）

- `setSignals({dataTerminalReady:false, requestToSend:false})` を**すべての `open()` と `reopen()` の後**に。片側だけは最悪
- **in-place のボーレート変更は無い** — `close()`＋`open()` になる。ネイティブは開いたハンドルの属性を変えるだけなので、
  **ボーレート切替は他のツールがやらないことをやっている**。切替時のみ出る不具合はまずここを疑う
- `bufferSize` はドライバの受信バッファではない（Mojo データパイプ容量）。**帯域は増えない**
- `navigator.serial` は DedicatedWorker でも使える（`requestPort()` のみ Window 限定）。移すなら**リンク全体**を移す

- Claude Code の GitHub 連携でパッチ PR を自動生成、CI（§5-7）を必ず通す
- **自動マージの範囲を分ける**
  - 自動マージ可：UI 文言・翻訳・単位表・読取専用のデコード表
  - **人間承認必須**：検証台帳、テレグラム、引数置換規則、リスク分類、前提条件、`dme-link` 配下の全変更
- 段階的デプロイ＋版数ピン。異常時は 8-2 のキルスイッチ＋ロールバック

> **懸念（再掲）**：完全無人の自動修正は、誤った修正が全ユーザーの実車に即日届く経路になります。
> 上の人間承認ゲートとキルスイッチをもって「自動化するが無防備ではない」形にします。

## 検証方法

1. **codec**：`ds2.ts` は純粋なのでオフラインで網羅テスト（チェックサム・フレーム異常系・エコー分類・ログイン鍵）
2. **デバイスシミュレータ**：破壊的経路を**テレグラム列**でアサート。ガード経路はトレースが**空**であることを確認
3. **mock link**：PRACTICE モードで全ワークフロー（破壊的部分含む）をハード無しでリハーサル
4. **リンク計測**：実測 wire 時間 vs 理論、`parked/total`。中央値で報告し、head と middle を別々にサンプルする
5. **実車/ベンチECU**：IDENT → 故障読取 → ライブ値の順に切り分け。ジョブ1件ずつ
   前提条件実測 → 実行 → リードバック → 記録 → 台帳追記
6. **デッドマン**：「武装中にブラウザを強制終了 → 解除されたか」をベンチECUで必ず確認
7. **Cloudflare**：デプロイURLを実機Chromeで開き、Web Serial 接続まで通す
