# 仮想車両での画面操作テスト — 項目

目的：仮想車両で通ったものは、実車でも同じ操作で同じように動く、と言えるところまで試す。
2026-11-19 の実車で、AI が SMG II のアクチュエータ駆動を「一度だけ」（pulse）で頼んだら、値の組が一つも返らなかった。
デモテストはその呼び方を通っていなかった。だから、**見本を一つ選んで試すのをやめ、全部の項目を、全部の入口と呼び方で試す**。

## 0. 原則

1. **数え上げる。** 項目は手で選ばない。動かす項目は `runCoverage` の一覧（E46 M3 567、M3 以外の E46 243）から、
   読む項目は各モジュールのジョブ表から、AI の道具は `tools.ts` の 36 個から作る。一覧が増えれば、試験も増える。
2. **入口ごと、呼び方ごと。** 同じ項目を、次の全部で通す。
   - 画面：ACTUATOR の RUN または START、SERVICE、ADAPTATION
   - AI：`monitoring_actuate` の pulse と start、値あり・値なし、`monitoring_procedure`、`monitoring_stage`
3. **線の上を見る。** 「started: true」で合格にしない。仮想車両が受け取ったバイト列を記録し、次の三つが EdiabasLib の電文と
   一致することを確かめる。
   - 送った順番
   - 宛先
   - 止めの電文（時間切れのときも）
4. **実車の振る舞いを練習の車に持たせる。** 実車でしか起きないことは、次の三つで出す。
   - 否定応答
   - 無応答
   - 状態の変化（車速・電圧・エンジン）
   条件を変えるのはシナリオで、正常の答えは EdiabasLib の模擬で返す。
5. **断る道も試す。** 断るべきときに断り、正しい理由を言うこと。誤った理由（今回の「組が無い」）は不合格。

## A. 仮想車両 — いまある練習の車と、足りないもの

仮想車両は新しく作らない。PRACTICE の練習の車（`packages/monitoring-engine/src/practiceCar.ts`・`practiceEcu.ts`）
を使う。デモテストはテスト用ビルドの口（`src/lib/e2e.ts` の `car.get / set / reset`）から、この車の状態を変える。

**もうあるもの**

| 何を | どこで |
|---|---|
| 後期 E46 M3（SMG II・DSC・ナビ）と、M3 以外の E46（MS43・GS20）の IDENT | `M3_IDENTS`・`NON_M3_IDENTS`、`idents` |
| 載っているモジュール。載っていないものは答えない | `fitted` |
| 車速・エンジンの回転・電圧 | `speedKmh`・`engineRunning`・`batteryV` |
| 故障メモリ。DME・各モジュール・DSC MK60（KWP）・MS43。消去の電文で実際に消える | `dmeFaults`・`moduleFaults`・`dscMk60`・`ms43Faults` |
| メーターの VIN の下 7 桁 | `clusterVin` |
| 線ごと落とす | `lineDown` |
| ナビの時計（サーバーの時刻を聞く） | e2e の `clock.hear` |
| 動かすジョブの答え。EdiabasLib の模擬が返したもの | `setPracticeAnswers`（`job-frames.oracle.json`） |

**足すもの（これが無いと、E の表とシナリオが実車の保証にならない）**

| # | 足すもの | なぜ | 合格 |
|---|---|---|---|
| A1 | 車が受け取ったバイト列の記録を、試験から読めるようにする | 「始まった」ではなく、送った順・宛先・止めの電文を EdiabasLib と比べるため（原則 3） | 練習の車が受け取った全電文が、時刻・宛先つきで試験から順に読める。読んだ分を消せる |
| A2 | 電文ごとに、否定応答（0xB0 など）・無応答・短い答え・遅い答えを返させる | `lineDown` は線ごとしか落とせない。実車の「その電文だけ断る」を出すため | 電文の頭（またはジョブ名）と回数を指定して、4 つのどれでも返せる。指定しない電文は今までどおり答える |
| A3 | 0x56 を前期（ASC MK20）に切り替える | いまは後期（DSC）だけ。前期の車で別の SGBD を選ぶことを確かめるため | 前期に切り替えると 0x56 が ASC MK20 として名乗り、DSC MK60 は答えない |
| A4 | 走りの筋書き：時刻ごとのギア・車速・回転・アクセル開度・吸気／排気カムの目標と実測・ノック・油温を、シナリオが書いて流す | いまは回転が車速から決まり、アクセルは 14 %、カムは 12° の一定値。ログを見て分析するシナリオ（SC13）には、答えの分かっている「谷」が要る | 筋書きの値が、DME のライブ値の読取でそのまま返る（回転 ±10 rpm、角度 ±0.5°、％ ±1）。筋書きが無いときは今までどおり |

## M. シナリオテスト — オーナーの目で

主語はオーナー。オーナーは次の三つでアプリを使う。

- **ナビ**：車の画面に MONITORING WORKS。走行中は見るだけ。
- **声**：別の電話の AI（Matrix）。走行中もこれで頼む。
- **PC**：停車して、家や店で。

**合格は、オーナーに見えるもの・聞こえるもの・手元に残るものだけで決める。**
- 見えるもの：画面の表示、札、ダイアログ、数字。
- 聞こえるもの：AI の答え。
- 残るもの：保存した記録、送った記録。

裏側の確かめ（電文が EdiabasLib と同じか）は、同じ実行の中で E と K が別に見る。裏側が正しくても、画面や答えで
オーナーに分からなければ、そのシナリオは不合格。

### M0. どのシナリオにも共通の合格基準

| # | 基準 |
|---|---|
| U1 | **押したら 1 秒以内に変わる。** 押せた・待っている・断った、のどれかが画面に出る。何も起きないのは不合格 |
| U2 | **断るときは、次にすることが分かる。** 画面の行の札（「練習から」「走行中」「値を選ぶ」など）と、AI の答えが同じ理由を言う。どうすれば動くかも言う（例：「PRACTICE で一度動かしてください」）。ゼロ件・空欄・英語の内部名だけは不合格 |
| U3 | **画面と AI が同じことを言う。** モジュールの名前・故障の件数・接続の状態・動いているもの |
| U4 | **動いている間は、それと分かる。** 何が動いているか・残り秒数・STOP が見える。止まったら消え、「止まった」が残る |
| U5 | **結果はオーナーの言葉で読める。** 故障は日本語の名前と状態（今出ている／散発）。値は単位つき。生のバイトは補足としてならよい |
| U6 | **AI の答えは聞いて分かる。** 結論が一文目。2〜3 文。日本語。ジョブ名や列名を言わない。ツールを呼ぶ前に「見てみます」 |
| U7 | **画面がガタつかない。** 通知や札が出ても消えても、ほかのボタンの位置が動かない |
| U8 | **VIN が出ない。** 走査の欄の下 7 桁のほかは、画面にも AI の答えにも記録にも出ない |

以下の表の「合格」は、U1〜U8 に加えて満たすこと。

### M1. ふつうのシナリオ（全機能）

#### SC01 はじめてつなぐ（ナビ）

| 手順 | オーナーの操作 | 合格（見える・聞こえる） |

| 1 | ナビで MONITORING を開く | STARTUP が出る。何をすればよいかが一行で書いてある |

#### SC02 警告灯が点いた（事後保全・声と画面）

車の状態：走行中 40 km/h。DSC に故障 2 件、エンジンに 1 件。

| 手順 | オーナーの操作 | 合格 |
|---|---|---|
| 1 | 声で「DSC のランプが点いた」 | AI「見てみます」→「DSC に故障が 2 件、エンジンに 1 件あります」。一件ずつ、名前と、今出ているか散発かを言う |
| 2 | ナビを見る | DIAGNOSIS に同じ 3 件。名前が日本語で、記録したときの条件（距離・温度・電圧）が読める |
| 3 | 走行中に「消して」 | AI「止まってから消せます」。画面の消去は押せず、札は「走行中」 |
| 4 | 停車して「消して」 | AI が、どのモジュールの何が消えるか（記録した条件も消える）を読み返し、「残してから消しますか？」と聞く |
| 5 | 「残して、いいよ」 | AI「保存して、消しました。読み直すと 0 件です」。画面も 0 件。SESSIONS に、消す前の記録が日時つきで残る |

#### SC13 走りながらログを見て、分析し、取り方と走り方を変える

ねらい：3 速で踏んだとき、4,000 回転あたりでトルクが抜ける気がする。走りながら画面で値を見て、AI と一緒に分析し、
見る値と取り方、次に取る走りの条件を変えて、再現させる。

練習の車の筋書き（A4）は、次の 3 段で流す。

- 0〜60 秒：一般道。2〜4 速で 20〜60 km/h。
- 60 秒：3 速で全開。3,000 → 6,000 回転を約 4 秒で上がる。このとき 3,900〜4,300 回転で、排気カムの実測が目標より最大 6.0° 遅れる。ノックは無し。
- 120 秒：同じ踏み方をもう一度。同じ遅れが出る。

表示される値は、この筋書きから決まる。

| 手順 | オーナーの操作 | 合格（画面の項目と値・AI の答え） |
|---|---|---|
| 1 | 停車中に声で「3 速で踏んだときのトルクの抜けを見たい。ログの準備をして」 | AI が、見る値を名前で言う（回転・アクセル開度・吸気カムの目標と実測・排気カムの目標と実測・車速・ノック）。「全部で 8 項目、毎秒およそ n 回取れます」と言う。DATALOG の「記録するチャンネルを選ぶ」に同じ 8 項目が選ばれ、「8 項目 / k ブロック = 1 サンプルあたり k 往復」が出る。CO-WORK の計画に「3 速で踏む（3,000→6,000 回転）」の段が出る |
| 2 | 「記録して」 | AI「記録を始めました」。画面の項目は次のとおり。 ①8 本のグラフ：名前・単位（rpm・%・°KW・km/h）と今の値つき。 ②実効レート（Hz）。 ③サンプル数（増えていく）。 ④記録中の印と経過時間。 HUB には回転と車速が大きく出る。ナビの幅では LIST と VISU が切り替えられ、どちらでも 8 項目が見える |
| 3 | 一般道を走る（0〜60 秒） | 画面の回転・車速・アクセルが筋書きと一致する（回転 ±10 rpm、車速 ±1 km/h、アクセル ±1 %）。グラフが途切れない。走行中に画面を触らなくてよい（触る必要のある表示が出ない） |
| 4 | 3 速で踏む（60 秒） | グラフに 3,000→6,000 回転の上がりが出る。排気カムの実測線が、3,900〜4,300 回転で目標線から離れる |
| 5 | 踏み終わってすぐ、声で「今の何？」 | AI が分析した時点を言う（「n 秒前、3 速、4,100 回転」）。「排気カムが目標より約 6 度遅れていました。ノックはありません」と答える。画面のグラフの同じ時刻にカーソルが立つ。カーソルの値が AI の数字と一致する（回転 ±50 rpm、角度 ±0.5°） |

## N. 画面のデザイン確認 — シナリオの手順ごとに

機能が合格でも、画面がばらばら・多すぎる・何の話か分からない、ではオーナーは使えない。
M のシナリオで画面が出る手順ごとに、撮った画面を次の三つの目で確かめる。結果は合否ではなく所見として残し、O の修正案の材料にする。
ただし、U1〜U8 に触れるもの（ガタつく、断る理由が分からない、など）は、シナリオの不合格にもなる。

拠りどころは `tsunagi-m-design`（六つの原則、色、罫、部品）と `tsunagi-m-ux`（一度だけ言う、説明の置き方、文言）。

### N1. 一貫しているか（D1）

| # | 確かめること | よい状態 |
|---|---|---|
| D1-1 | 色 | 三色（青・赤・紫）と中立のグレーだけ。同じ意味に同じ色（青は押せる・選んだ・正常、赤は危ない・故障、紫は動作中・注意）。四つ目の色相が無い |
| D1-2 | 字 | 車から読んだ値（回転・コード・時刻・電圧）は等幅、ラベルとボタンはサンセリフ。同じ種類のものが画面ごとに違う字になっていない |
| D1-3 | 部品 | 行・札・ボタン・ダイアログが `ui.tsx` の同じ部品。同じ役目のものの大きさ・余白・角が画面ごとに違わない |
| D1-4 | 罫 | 罫は領域と領域の間だけ。物を枠で囲んでいない |
| D1-5 | 位置 | 同じ操作は同じ場所。START／STOP、確認の実行、モジュールの選択、記録の印が、タブを替えても同じ位置にある |
| D1-6 | 語 | 一つのものに一つの語。タブ・ボタン・ダイアログ・記録の行・AI の答えが同じものを同じ名前で呼ぶ（例：「油圧ポンプ」をある所では HYDROPUMPE、ある所では「ポンプ」と呼ばない） |
| D1-7 | 言語 | 一つの文に日本語と英語の内部名が混ざらない。ジョブ名は補足の位置にだけ出る |
| D1-8 | 状態の見せ方 | 動作中・待っている・断った・止まった・完了が、どの画面でも同じ見せ方（同じ札・同じ色・同じ場所） |

### N2. 削ぎ落とされているか（D2）

手順ごとに、画面に出ている要素（文・数字・ボタン・札・グラフ・アイコン）を数え、一つずつ問う。
「この手順で、オーナーはこれを見るか、押すか」。どちらでもない要素は「削れる候補」として記録する。

| # | 確かめること | よい状態 |
|---|---|---|
| D2-1 | 使わない要素 | この手順で見も押しもしない要素が 0。あれば、消す・まとめる・奥（ⓘ の中）へ、のどれかを案にする |
| D2-2 | 二度言い | 同じ情報が同じ画面に二度出ない（見出しと札、札と説明文が同じことを言っていない） |
| D2-3 | 説明の置き場所 | 長い説明は主題の所の ⓘ の奥にある。帯や行の中に段落が出ていない |
| D2-4 | 走行中の画面 | 走行中に出る画面（HUB・DATALOG・PROBE）は、一目で読める数だけ。値は大きく、ラベルは短い。走行中に押す必要のある要素が無い |
| D2-5 | 飾り | 意味の無い色・影・枠・アイコン・アニメーションが無い |
| D2-6 | 数え方 | 手順ごとに、要素の数・押せるものの数・色の数・文字数を記録し、版ごとに比べる。増えたら理由がある |

### N3. 一つの話になっているか（D3）

| # | 確かめること | よい状態 |
|---|---|---|
| D3-1 | 3 秒で一文 | 画面を 3 秒見たオーナーが、「いま何が起きていて、次に何をするか」を一文で言える。言えた一文が、そのシナリオの手順の意図と同じ |
| D3-2 | 主役が一つ | 画面の主役（一番目に入るもの）が一つで、それがこの手順の主題。主役になりたがる要素が二つ以上ない |
| D3-3 | 読む順と手順の順 | 上から（左から）読む順が、オーナーのする順と同じ。確認ダイアログは「何が → いつまで → 押すと何が起きる」の順 |
| D3-4 | 画面と声が同じ話 | AI の一文目と、画面の見出し・主役が同じことを言う |
| D3-5 | 切り替わりの理由 | AI が画面を切り替えたとき（ACTUATOR へ、PROBE へ）、なぜこの画面になったかが画面で分かる（何のための画面かの見出し） |
| D3-6 | シナリオ全体 | 一つのシナリオの頭から終わりまで、画面がつながった一つの話に見える。手順の間で、前の画面の文脈（どの部品・どの調査）が消えていない |

### N4. どう確かめるか

- **機械で見るもの**：D1-1・D1-2・D1-4・D1-8・D2-6 と、ガタつき。
  - 撮った画面と DOM から、色の値・字の種類・裸の枠・状態の見せ方・要素の数を数える。
  - 既存の `tools/check_ui_tokens.mjs` を手順ごとの画面に広げる。
- **目で見るもの**：D1-3・D1-5・D1-6・D1-7・D2-1〜D2-5・D3 の全部。
  - 撮った画面と、その手順の意図（シナリオの表の「オーナーの操作」）だけを渡したレビュアーが判定する。
  - レビュアーは別の AI エージェントで、コードは見せない。D3-1 では、まず画面だけから一文を書かせ、そのあとで意図と比べる。
  - 運営者が最後に、所見の一覧を見て直す・直さないを決める。
- **記録**：手順ごとに、画面・D1〜D3 の判定（○／△／×）・削れる候補・一文を一行に残す。版ごとに並べて比べられるようにする。

## O. UX 修正案のまとめ — 計画の最後

テストが一回りしたら、N の所見をまとめて修正案にする。直すのはそのあと、運営者が選んでから。

### O1. まとめ方

1. **画面ごとに集める。** シナリオの手順の所見を、画面（STARTUP・DIAGNOSIS・DATALOG・ACTUATOR・SERVICE・ADAPTATION・PROBE・SESSIONS・HUB・確認ダイアログ・ヘッダ）ごとに束ねる。
2. **同じ原因をまとめる。** 同じ部品や同じ語から来る所見は一つの案にする（例：「状態の札が画面ごとに違う」→ 札を一つの部品に）。
3. **引き算から考える。** 足す案より先に、消す・まとめる・奥へ、の案を出す。足す案は、消しても足りない理由を書く。
4. **順番を決める。**
   - 先に、走行中に見る画面（HUB・DATALOG・PROBE）と、車を動かす前の確認ダイアログ。
   - 次に、オーナーが毎回通る画面（STARTUP・DIAGNOSIS）。
   - 最後に、たまに使う画面。

### O2. 修正案の書き方（一案ごと）

| 欄 | 中身 |
|---|---|
| 画面 | どの画面のどこか |
| 見つけたもの | どのシナリオのどの手順で、D1〜D3 のどれに当たったか。撮った画面 |
| 案 | 何をどうするか。消す・まとめる・奥へ・揃える・足す、のどれか |
| 前と後 | 今の画面と、案を当てた画面の絵（簡単なもの） |
| 効き目 | 要素の数・押せるものの数・文字数がどう減るか。3 秒の一文がどう変わるか |
| 影響 | 変わる部品とほかの画面。TUNER など、同じ部品を使うほかの M ツールへの影響 |
| 大きさ | 小（文言・余白）・中（部品の差し替え）・大（画面の作り直し） |

### O3. 出すもの

- 修正案の一覧（O2 の表を案の数だけ）を一つの文書にする。画面と前後の絵つき。
- 運営者が案ごとに「直す・あとで・直さない」を決める。
- 直すと決めた案は、小さい順に PR にする。各 PR でもう一度 M と N を回し、所見が減ったことを数で示す。
- `tsunagi-m-design`・`tsunagi-m-ux` の規則そのものを変える案は、M ツール全体の話なので、Skill の正本（tsunagi-m）への提案として別に出す。

## P. 進め方

1. 練習の車に A の 4 つを足す（電文の記録、電文ごとの否定応答、前期 0x56、走りの筋書き）。
2. B〜J の項目と、M のシナリオを試験にする。
3. 試験を回し、機能の不具合を直す（ここまでで機能は合格）。
4. 同じ実行で撮った画面で、N のデザイン確認をする。
5. O の UX 修正案をまとめ、運営者が選ぶ。
6. 選んだ案を直し、M と N をもう一度回して確かめる。

## K. 合格の決め方

- **シナリオ（M）の合否は、オーナーに見えるもの・聞こえるもので決める（M0 の U1〜U8 と各手順の「合格」）。**
  試験は各手順で画面を撮り、AI の答えの文を残す。報告は、その画面と文を並べて、どの基準で落ちたかを書く。
- 電文の一致（原則 3）は、同じ実行の中で裏側として確かめる。シナリオの合格の代わりにはならない。両方通って配信する。
- E の表は、項目数 × 入口の数だけ行がある。1 行でも落ちれば配信しない。
- 落ちた行は、項目・入口・送った電文・期待した電文・返した理由を報告に並べる。
- 仮想車両で試せないもの（次の三つ）は、試験が「実車でだけ確かめる」と明記して数える。
  - 本物のモジュールが EdiabasLib の模擬と違う答えを返すこと
  - 部品が本当に動くこと（音・圧・動き）
  - ケーブルとナビの USB の電気的な振る舞い
