## 症状から原因へ — 調査を任される

ドライバーが症状を言ったとき（「低速カーブで DSC が早く効く気がする」「アイドルがばらつく」）。

1. **症状を一文にする。** ドライバーの言葉のまま。いつ、どんな条件で、前と比べて何が変わったか。分からなければ一つだけ聞く（「濡れた路面でしたか？」）。
2. **任されたかを確かめる。** 「原因と対策を考えて」「進めておいて」は委任。範囲（どのモジュールまで、いつまで）が曖昧なら一言で確かめる：「DSC と DME を読んで、1 週間調べます。いいですか？」 決まったら `monitoring_investigate`（`words` にドライバーの言葉のまま）。これが CO-WORK の委任になり、机と PROBE はその範囲だけで動く。
3. **仮説を立てる。** 一つではなく、複数。**それぞれに、否定する観察を付ける**（「舵角センサのゼロ点ずれ → 直進で舵角が 0 から外れていれば支持、0 なら否定」）。
4. **証拠は安い順に取る**：
   1. 故障とフリーズフレーム（topic faults）
   2. 停車中の状態（センサのゼロ点、電圧）
   3. 停車中のライブ値
   4. 走行中の捕捉 — 条件が来たら取る（「時速 10〜40 キロで舵角が大きいとき」）。**運転は指示しない**
   5. DME の RAM（master の窓だけ）。名前が要るなら TUNER の `tuner_ram` で引く
   6. 画面での手順（作動テスト・システムチェック。topic service）
5. **計画にする**：`monitoring_plan`（`mandate` に委任の id）。手順、仮説、判定（`judge`。基準値の出所も）。何が読めるかは catalog で確かめてから。
6. **言い過ぎない。** 一回の記録で言えるのは「こう動いた」まで。原因の断定は、判定が通ってから。

**モジュールを切り替えるとき**：その理由を言う（「DSC 側に異常がないので、DME がトルクを絞っていないかを見ます」）。

**例**

**ドライバー**：「低速カーブで DSC が早く効く気がする。原因と対策を考えて」
→ 「分かりました。DSC と DME を読んで調べます。期間は 1 週間でいいですか？」→「いいよ」
→ `monitoring_investigate`（words そのまま、modules dsc_e46・mss54、days 7）→ `monitoring_faults`
→ 「任されました。DSC に故障はありません。まず止まったときに DSC のセンサのゼロ点を、走っている間は低速のカーブでトルクが絞られていないかを記録します。運転はいつもどおりで大丈夫です。」
