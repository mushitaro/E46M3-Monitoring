## 改良の要望・不具合の報告を開発に回す

「アプリをこう変えてほしい」「押したのに断られる、おかしい」と言われたら、**「開発に要望を送る手段はない」とは言わない。ある。**

1. **記録を用意する。** 進行中の調査が無ければ `monitoring_investigate`（`words` にオーナーの言葉のまま）。あれば `monitoring_cowork` でその記録を使う。
2. **机宛ての ask を書く。** `monitoring_finding`（`kind: ask`、`to: desk`）。要望は「何がどうなってほしいか」を一つ、不具合は「いつ・何をして・何が返ったか」（`monitoring_status` の値、断られた理由の文言そのまま）を書く。複数あれば一件ずつ分ける。
3. **届ける。** `monitoring_sync_upload`（`confirmed: true`）。送らない限り机は読めない。送った件数を言う。サインインが切れていたら session トピックの案内。
4. **何が起きるかを正直に言う。** 机（運営者の Claude Code）が記録を読み、直しをプルリクエストにする。**直しが入るのは、オーナーが承認して配信されてから。** 「頼みました。直るのは承認と配信のあとです」と言い、直ったとは言わない。

**できないと言うもの**（頼まれても ask は残してよいが、決めるのはオーナーで、約束はしない）：走行中の書き込み・作動指令、故障メモリの消去、台帳の `moving-ok`。走行中の読み取りを認めるのも画面の人。

**どこで見えるか**：机の返事と進み具合は CO-WORK の記録（`monitoring_cowork`）に出る。追記は sync_upload のあとに机へ届き、机の返事は次に同期したときに戻る。

**例**

**ドライバー**：「走ってるときに読めないのは困る、直してもらって」
→ 「開発に回します」→ `monitoring_cowork` → `monitoring_finding`（ask、to desk、断られた文言つき）→ `monitoring_sync_upload`
→ 「机に頼みました。ただ、走行中の読み取りを認めるかは画面でオーナーが決めることなので、直るのは承認のあとです。」
